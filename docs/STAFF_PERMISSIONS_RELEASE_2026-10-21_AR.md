# مراجعة إصلاح صلاحيات الموظفين والنشر — 2026-10-21

الإصدار يصلح توافق الصلاحيات بين الخادم والواجهة، ويلغي اشتراط أرقام Batch أو علامات داخل رسالة Commit. لا يضيف صلاحيات للحسابات ولا يغيّر أسعارًا أو حالات طلبات أو قواعد المحاسبة.

## التغييرات

| الجزء | النتيجة | الملفات الأساسية |
| --- | --- | --- |
| المخزون | `inventory.manage` يقرأ سياق المخزون ويكتب القطع فقط؛ لا يعدّل الموديلات أو أسعارها، ولا يحذف السجلات غير المرسلة عند الحفظ الكبير | `backend/src/modules/catalog/catalog.routes.ts`, `src/dashboard/catalog-admin.js` |
| القراءة والواجهة | `catalog.read` يحمّل البيانات؛ الأزرار والنماذج والحفظ المشترك ومؤقتات التحديث تتبع الصلاحيات الفعلية | `src/dashboard/staff-permissions.js`, `Eye/dart-admin-auth.js`, `Eye/dart.js`, `Eye/dart-domain-state.js`, `Eye/dart-orders-api.js`, `Js/dart-catalog.js` |
| مواقع المندوبين | منع الإحداثيات الحية بدون `representative_location.read` في الردود الكاملة والجزئية والمتداخلة، مع إبقاء دبابيس عنوان العميل وتتبع العميل لطلبه | `backend/src/middleware/representative-location-access.ts` |
| إدارة الموظفين | الواجهة تستخدم `canManageStaff` من الخادم لإظهار إجراءات Owner؛ تبقى حماية Owner الخادمية قائمة | `backend/src/modules/identity/identity.service.ts`, `src/dashboard/staff-admin.js` |
| التواصل والتقييمات | فصل القراءة والحفظ حسب `contacts.*` و`reviews.*`، مع إتاحة رسائل التواصل القديمة وحماية التقييمات والرسائل غير المرئية من الحذف | `backend/src/modules/dashboard/dashboard-state.service.ts`, `Eye/dart-domain-state.js`, `Eye/dart.js` |
| النشر | مقارنة الملفات المتأثرة فقط؛ الرسالة العادية وRedeploy وبداية المشروع لا تتطلب تغيير Batch | `scripts/vercel-ignore-frontend.sh`, `backend/scripts/vercel-ignore-backend.sh`, `AGENTS.md`, `docs/DEPLOYMENT_BATCHING.md` |

ملفا `Eye/dart-staff.js` و`Eye/dart-permissions.js` ناتجان مضغوطان من المصدر المقروء داخل `scripts/`. حد الزيادة الإجمالية في JavaScript الأساسي 5 KiB مقارنة بالحد السابق، وزيادة الحد الخاص بالملفات المؤجلة 1 KiB. حد Home المباشر 225 KiB وحد الملف الواحد 260 KiB لم يتغيرا. تتحقق الاختبارات من بصمات المصدر والحدود المنفصلة للملفات الجديدة.

## API وقاعدة البيانات

- لا توجد جداول أو أعمدة أو Migrations جديدة، ولا تنفيذ لعمليات على بيانات Production أثناء التطوير.
- تغيّرت بوابات `GET/PATCH/PUT /api/v1/admin/catalog-state`، وأضيف حجب إحداثيات المندوب إلى ردود الإدارة.
- `GET /api/v1/admin/staff` يعيد `canManageStaff`؛ الحقل يساعد العرض ولا يمنح سلطة.
- قراءة `domain-state` للتقييمات تستبعد Contact Us. قراءة التواصل تجمع مخزني الرسائل القديم والحالي. عند حفظ تواصل مصرح به، تُجمع الرسائل في مخزن التواصل داخل Transaction مع إبقاء التقييمات؛ لا توجد عملية نقل جماعية عند النشر.
- إصدارات التواصل تتتبع المخزنين. قفل السجلين و409 يحميان رسالة تصل أثناء التعديل. يعيد حفظ التقييمات والتواصل `relatedVersions`، والمتصفح يسلسل حفظهما ويحدّث الإصدارات المعروفة فقط.
- `catalog.edit` وكتابة الأقسام الأخرى لا يمنحان القراءة تلقائيًا. يحتاج محرر الأقسام إلى صلاحية القراءة المقابلة كما هو موضح بجوار الاختيارات. تبقى صلاحيات الإدارة العامة بدائل للصلاحيات الدقيقة في المسارات التي كانت تدعم ذلك بالفعل.

## التحقق المحلي

| الفحص | النتيجة |
| --- | --- |
| `cd backend && npm run check` | Lint وTypeScript و396 اختبارًا ناجحًا؛ 47 اختبارًا في 6 ملفات تتطلب `TEST_DATABASE_URL` ولم تعمل محليًا |
| `cd backend && npm run build` | ناجح |
| مجموعات `ciStatic` في `tests/test-inventory.json` | 31 مجموعة ناجحة |
| مجموعات `ciBrowser` | 8 مجموعات ناجحة، ومنها full-site واختبارات المخزون وContact Us والتقييمات بصلاحيات مستقلة |
| `navigation-browser.cjs` | سيناريو Back/Forward cache يتطلب Chromium الكامل؛ headless shell المحلي يعيد `BackForwardCacheDisabledForDelegate`. Chromium الكامل محليًا محجوب عند إنشاء ProcessSingleton socket. يبقى هذا الاختبار مفعّلًا دون تخفيف في CI |
| OpenAPI وGit | YAML سليم ومعرّفات العمليات فريدة؛ `git diff --check` ناجح |

السيناريوهات الجديدة تختبر رفض تعديل الموديلات والأسعار من حساب مخزون، حفظ القطع الكبير دون حذف السجلات غير المرسلة، حجب الموقع في الردود المتداخلة والجزئية، بقاء تتبع العميل، توقف الاستعلامات المرفوضة، حراسة النماذج والنقر المباشر، بقاء حالة التحميل، عرض Staff لغير Owner، فصل التواصل عن التقييمات، حفظ المخزنين بالتتابع، وحماية الرسائل المتزامنة باستخدام SQL فعلي داخل PGlite معزول. وتختبر سياسة النشر برسائل عادية في Git مؤقت للواجهة والخادم والتغيير المختلط والتوثيق والتاريخ المفقود وRedeploy.

## تجربة التشغيل

1. من Owner، افتح Settings → Staff ومنح حساب تجريبي `catalog.read` فقط. تأكد من تحميل الموديلات والقطع وغياب أزرار التعديل.
2. اختبر `inventory.manage` فقط: أضف قطعة أو عدّلها، أعد تحميل الصفحة، وتأكد من بقاء السعر والموديلات دون تعديل. جرّب إرسال موديل يدويًا إلى API وتوقّع 403.
3. اختبر `orders.read` دون `representative_location.read`: بيانات الطلب وعنوان العميل موجودة، وموقع المندوب محجوب. أضف صلاحية الموقع وتأكد من ظهوره.
4. اختبر `contacts.read/manage` دون `reviews.*`، ثم العكس. افتح سجلًا وعدّله وأعد التحميل؛ يجب أن يُحفَظ في قسمه وحده، ولا تظهر رسائل التواصل الخاصة لحساب التقييمات.
5. اختبر حساب `staff.read` غير Owner: يستطيع قراءة الدليل، ولا تظهر له دعوة الموظفين أو تعديل الصلاحيات. تأكد أن API يرفض التعديل أيضًا.
6. انشر Commit عاديًا بلا علامات Batch أو Deploy؛ يكتشف كل مشروع الملفات المؤثرة. راجع SHA وحالة READY وProduction alias للموقع والـAPI ثم اختبر الصحة وتحميل الأصول.

التراجع البرمجي يكون بـGit revert للإصدار وإعادة النشر. لا يوجد تراجع Schema. راعِ أن نسخة أقدم من خدمة Feedback كانت تعرض Contact Us داخل مخزن التقييمات؛ لا تُعد تلك النسخة بعد تحرير رسائل بالنسخة الجديدة دون مراجعة توافق عرض الرسائل.
