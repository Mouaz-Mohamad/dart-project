# تجربة Dart المباشرة بدون مزوّد إضافي — 3 نوفمبر 2026

**الحالة: تجربة محلية معزولة تعمل، وليست تفعيلًا على المتجر أو الداشبورد الإنتاجي.** لا حساب Ably، ولا Redis، ولا خدمة رسائل إضافية، ولا ترقية خطة. طلب المالك الحالي هو استعمال Vercel وPostgreSQL الموجودين فقط؛ وثيقة التجربة السابقة تاريخية وليست طلب إعداد حساب خارجي.

## ما تغير

- ملفات التجربة الجديدة فقط: `backend/experiments/direct-realtime/`، واختبارات `backend/tests/direct-realtime.test.ts`. لا استيراد منها في تطبيق الإنتاج. لا تعديل على حزم الاعتماد في المشروع.
- `schema.sql` هو **fixture** يتطلب schema معزولًا وعلم تشغيل خاصًا. يضيف `pg_notify` إلى حدث إصدار الطلبات داخل معاملة الحفظ نفسها؛ لا إشعار من معاملة متراجَع عنها، ولا عامل نشر أو نداء دوري يسأل عن أحداث جديدة. السجل التجريبي منفصل عن رسائل WhatsApp/Email.
- `notifications.ts` يفتح اتصال PostgreSQL مباشرًا واحدًا لكل feed/نسخة خادم ويستخدم `LISTEN`. المشتركين داخل النسخة يتشاركونه؛ نسخ الخادم المختلفة تستقبل الإشعار من قاعدة البيانات نفسها. آخر مشترك يخرج يغلق الاتصال، وفقد اتصال DB يغلق التدفقات ليعاد الاشتراك والاستدراك. لا تُستخدم ذاكرة نسخة الخادم لتخزين الحالة الدائمة أو تنسيق النسخ.
- `router.ts` يرسل SSE إلى الواجهة بعد تطبيق جلسات Dart وMFA وصلاحية `orders.read` المركزية، ثم يعيد تطبيقها قبل كل دفعة إشعارات. فقد الصلاحية يغلق التدفق قبل إرسال الإشعار التالي؛ انتهاء مدة التدفق يجبر مصادقة جديدة أيضًا. لا توجد دعوى بأن اتصالًا خاملًا يُغلق فور تغيير الصلاحية دون حدث؛ لا تُرسل بيانات بعد السحب دون إعادة التحقق.
- الرسالة تحمل UUID وإصدارًا فقط، بلا عميل أو هاتف أو عنوان أو تفاصيل أوردر. دمج دفعات الإشعارات، حد مشتركين للنسخة وحد تدفقين للجلسة، وقطع المستهلك البطيء يحصرون الذاكرة والطوابير. الردود private/no-store والتدفق من نفس الأصل.
- `event-source.ts` يستخدم EventSource الأصلي في المتصفح، مع timeout لبدء الاتصال. حالة العميل الموجودة تتجاهل الإصدارات القديمة، تجمع التغييرات، وتمنع الرد المتأخر بعد logout.
- `source.ts` يستدرك بعد reconnect عبر رقم الإصدار الصغير أولًا. ينزّل snapshot كاملًا فقط إن تغير الإصدار. نسخة البيانات في الذاكرة فقط؛ لا localStorage أو IndexedDB. الصفحة التجريبية تقفل الاتصال بالخلفية وتعيده عند الرجوع.

`NOTIFY` ليس سجل إعادة تشغيل دائمًا. لذلك يبدأ الاشتراك قبل أول قراءة، وكل اتصال جديد يراجع الحالة المعتمدة في DB؛ لا نعتمد على وصول إشعار جديد لاحقًا لإصلاح فقد آخر تحديث.

## الواجهات والـmigration

في تطبيق التجربة المحلي فقط: `GET /direct/events` و`GET /direct/version` و`GET /direct/snapshot`، كلها للقراءة ومحكومة بصلاحيات الموظف. لا endpoint جديد في API الإنتاج، ولا migration إنتاجية، ولا تعطيل polling الحالي. لا تنفّذ fixture SQL على الإنتاج.

## النتائج المقاسة

التجربة شغّلت migrations النظام و`CommerceService.checkout` الحقيقي على بيانات اصطناعية، ونقلت الحدث عبر HTTP/SSE فعلي إلى قارئ تدفق. محرك PostgreSQL المحلي هو PGlite؛ وصلة LISTEN المحلية تمر عبر واجهته داخل نفس العملية، **وليست إثباتًا لاتصالات PostgreSQL الأصلية عبر TCP أو نشر Vercel**.

| المقياس | النتيجة المحلية |
| --- | ---: |
| خدمات إضافية / طلبات لمزوّد خارجي | 0 / 0 |
| قراءات بيانات الواجهة | 2: أول تحميل ثم التغيير |
| اتصالات LISTEN / أوامر الاشتراك | 1 / 1 |
| إشعارات تغيير تلقائية | 1 |
| قراءات بيانات أو LISTEN إضافية خلال 150ms خمول مقاس | 0 |
| JSON ردود البيانات / جسم SSE | 1,827 / 128 بايت |
| من بدء checkout إلى استقبال الإشعار محليًا | 85.05ms |
| الأوردر المحفوظ ظاهر في snapshot | نعم |

الزمن يشمل تنفيذ checkout، وليس زمن شبكة الإنتاج أو وعدًا بزمن توصيل ثابت. البايتات تستبعد HTTP/TLS والتوكنات وباقي اليوم؛ لا توجد نسبة توفير فاتورة أو إنترنت مثبتة. النتيجة الخام: `direct-realtime-results-2026-11-03.json`.

اختبار Chromium باستخدام **EventSource الأصلي** نجح: أول أوردر ظهر بعد قراءتين، ثم أُنشئ أوردر ثانٍ أثناء offline وظهر بعد reconnect دون انتظار أوردر ثالث. لم تحدث قراءة إضافية في فترة الخمول القصيرة المقاسة، ولا أخطاء JavaScript. الاختبار يقصّر عمر التدفق إلى 1.2 ثانية للتحقق من انتهاء الاتصال واستعادته؛ القيمة العادية في التجربة 240 ثانية.

## التحقق وإعادة الاختبار

نجحت فحوص إعداد Vercel وESLint وTypeScript والبناء، و669 اختبار خادم محليًا؛ تجاوزت البيئة 53 اختبارًا بشروط PostgreSQL الخارجية. نجحت أيضًا اختبارات التجربة الـ13، وفحص سلطة قاعدة البيانات على تخزين المتصفح، و`git diff --check`. نجاح المحلي لا يساوي نجاح TCP/الإنتاج؛ الحدود مفصلة أدناه.

```bash
cd backend
npx tsc -p experiments/direct-realtime/tsconfig.json
npx eslint experiments/direct-realtime tests/direct-realtime.test.ts
npx vitest run tests/direct-realtime.test.ts
node --import tsx experiments/direct-realtime/run.ts
node experiments/direct-realtime/browser-check.mjs
```

اختبار المتصفح يستعمل تجهيز Playwright/Chromium نفسه المتاح لاختبارات المشروع، ويمكن تحديد المتصفح المثبت بـ`CHROMIUM_EXECUTABLE`. لا يضاف اعتماد إنتاجي جديد.

الـ13 اختبارًا تغطي: checkout وإعادة المحاولة، منع الإشعار قبل commit/بعد rollback، وصول الحدث إلى feedين مستقلين ومشاركة listener داخل الواحد، عدم القراءة الدورية عند الخمول، إلغاء صلاحية/جلسة فعلية عبر middleware، منع الأصل الآخر وحدود التدفقات، انقطاع قاعدة البيانات واستدراك آخر حدث مفقود، burst وJSON غير صالح، انتهاء عمر التدفق وإغلاق listener، غياب تركيب الإنتاج وحارس fixture، فشل listener وحد سعته، رفض البيئة الإنتاجية والاتصال pooled أو غير المحلي، تهيئة EventSource واستعادته ومهلته، ومراجعة الإصدار الصغيرة بعد reconnect بدل إعادة تنزيل القائمة بلا تغيير.

إذا ضُبط `TEST_DATABASE_URL`، تستخدم الاختبارات `pg.Client` الأصلي لاتصالات LISTEN مستقلة، مع schemas مؤقتة. الحارس يقبل loopback فقط وقاعدة باسم `dart_test` أو `dart_pilot…`، ويرفض `DATABASE_URL` وVercel وبيئة production. CI المشروع الموجود يستخدم PostgreSQL 17 أصليًا على loopback؛ تشغيله هو تحقق TCP المنفصل عن نتيجة PGlite أعلاه. بيانات حساب HTTP اصطناعية، بينما تطبيق صلاحيات HTTP هو الموجود في Dart.

## الاستضافة والتكلفة: الحد المتبقي قبل التفعيل

- إعدادات مشروع API الموجودة تحتوي أسماء متغيرات للاتصال المباشر/unpooled؛ لم نغيّرها أو نكشف قيمها. وجود الاسم لا يثبت نجاح LISTEN وصلاحياته على الإنتاج.
- Vercel يدعم التدفقات، لكن مدة الوظيفة محدودة. التجربة تنهي الاتصال عند 240 ثانية؛ EventSource يعيد الاتصال، وبعدها تحصل مراجعة إصدار. لذلك لا يعني إيقاف polling كل 3 ثوانٍ أن عدد الطلبات سيصبح صفرًا طوال اليوم. عند الخمول المستمر، العمر 240s يعني نظريًا نحو 15 إعادة اتصال ومراجعة إصدار بالساعة لكل تبويب ظاهر، بالإضافة إلى المصادقة وkeepalive.
- keepalive كل 15 ثانية تعليق اتصال صغير بلا استعلام بيانات أو إعادة مصادقة دورية. يعاد فحص الصلاحيات عند الاتصال وقبل كل دفعة تغيير. اتصال DB يعاد إن انتهى أو توقف Neon/انقطع، مع استدراك من المصدر المعتمد.
- الاتصال المفتوح يحتفظ بذاكرة Vercel أثناء الطلب؛ وقد تستهلك إعادة الاتصال/الاستعلامات وقت تشغيل قاعدة البيانات. **عدم وجود اشتراك خارجي جديد لا يثبت أن فاتورة الاستضافة الحالية لن تزيد.** بيانات الفوترة الحالية وحدها لا تحدد أثر تشغيل SSE المستقبلي؛ لا تُنشر بيانات الفاتورة أو الأسرار في المستودع.
- لا ترقية أو شراء أو تغيير حدود الإنفاق أو تعطيل scale-to-zero. يلزم قبل التفعيل قياس محدود على Vercel/قاعدة الإنتاج الفعلية، ومراجعة الحصص والذاكرة والمصادقة والاتصالات المتزامنة، وإعداد احتفاظ سجل الأحداث. لا توجد تجربة حمل أو ضمان تكلفة صفر هنا.
- بعد قبول القياس، الربط التدريجي يبدأ بقراءة الطلبات الواحدة؛ عندها فقط يُوقف poll المقابل أثناء الاتصال السليم. تعميم الأقسام أو GPS خارج هذه التجربة.
