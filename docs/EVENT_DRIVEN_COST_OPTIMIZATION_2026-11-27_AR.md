# Dart — قرار هندسي وخطة تحسين الأداء والتكلفة

**التاريخ:** 27 نوفمبر 2026  
**الحالة:** قرار تصميم معتمد من صاحب المشروع بشأن القيود؛ التنفيذ والاختبارات المستقبلية لم تبدأ.  
**النطاق:** المتجر، Dart Eye، API، الإشعارات، الرسائل، المخزون، المالية، المندوب والمهام الخلفية.

## 1. الهدف والقيود الملزمة

اختيار Hybrid Event-Driven Serverless باستخدام البنية الحالية فقط: Vercel وNeon PostgreSQL وGitHub Actions والكود والمكتبات الموجودة بالفعل.
- ممنوع إضافة مكتبات أو حزم npm أو خدمات أو اشتراكات جديدة؛ لا Cloudflare ولا QStash ولا Redis ولا وسيط Realtime خارجي. أي استثناء يحتاج موافقة صريحة مسبقة من صاحب المشروع.
- لا تغيير للاستضافة أو قاعدة البيانات أو إطار العمل ولا إعادة بناء المشروع من الصفر.
- تقليل استدعاءات API واستعلامات SQL ومدة تشغيل Functions وذاكرتها ووقت نشاط Neon، مع سرعة وتجربة شراء ممتازة.
- قاعدة البيانات هي المصدر الموثوق للبيانات. لا تستخدم Cache أو الإشارات المحلية كمرجع للسعر النهائي أو المخزون أو الصلاحيات.
- لا إلغاء لوظائف المتجر ولا تعطيل للشراء أو تتبع رحلة نشطة أو إشعارات ضرورية أثناء ساعات الهدوء. لا تغيير لسياسات العمل ومواعيد الرسائل دون موافقة.
- تنفيذ المراحل بالتوالي واختبار كل مرحلة قبل التالية. لا نشر لتغييرات التشغيل قبل اعتماد الإصدار والتحقق منه.

## 2. مراجعة البدائل

هذه مراجعة هندسية من خمس زوايا (المعمارية، البيانات، الأداء، التكلفة، الموثوقية)، وليست نتائج تشغيل خمسة نماذج LLM مستقلة.

| البديل | المزايا | العيوب | القرار |
| --- | --- | --- | --- |
| Adaptive Polling فقط | بسيط ولا يحتاج خدمات إضافية | استمرار طلبات بلا تغييرات وتأخير محتمل | احتياطي محدود فقط |
| SSE / LISTEN-NOTIFY الحالي | تحديث لحظي وإعادة استخدام الموجود | اتصال مباشر طويل بـNeon وVercel وإعادة اتصال | انتقائي، مع قياس التكلفة |
| Managed Realtime / Task Queue خارجي | يفصل الاتصالات والجدولة | خدمة جديدة وتكلفة وتعقيد | مرفوض حسب قرار المالك |
| VPS أو تغيير الاستضافة | تحكم كامل | صيانة وانتقال وبنية جديدة | غير مطلوب |
| Hybrid Event-Driven داخلي | Cache، تنفيذ عند الحاجة، Outbox، Push، جدولة منفصلة | يحتاج ضبط الاتساق والتعافي وقياسًا فعليًا | الخيار المعتمد |

## 3. نتائج الفحص الأولي

الأدلة التالية من مراجعة ملفات الفرع main؛ لا تعني أن كل إعداد افتراضي مستخدم فعليًا في الإنتاج.

- [GitHub Outbox Worker](../.github/workflows/outbox-worker.yml): يستيقظ المجدول كل 5 دقائق، ويفحص السياسة قبل الاتصال بالـAPI. افتراضيًا الفاصل 15 دقيقة وساعات الهدوء 01:00–12:00 بتوقيت القاهرة. [سياسة الجدولة](../scripts/background-schedule.mjs). قد تتأخر GitHub Actions؛ ليست ضمانًا لموعد دقيق.
- [إعداد Vercel Backend](../backend/vercel.json): لا توجد Cron Jobs معرفة في هذا الملف.
- [app.ts](../backend/src/app.ts): تنظيف الحجوزات، تنظيف rate limits وتجهيز أعياد الميلاد مجمعة مع معالج Outbox.
- [Outbox dispatch](../backend/src/modules/outbox/outbox.dispatch.ts): الإرسال الفوري بعد الأحداث موجود بالفعل؛ معالجة الرسائل المؤجلة والفاشلة تحتاج مسار تعافٍ دائم.
- [Change feed](../backend/src/modules/changes/change-feed.ts) و[Change routes](../backend/src/modules/changes/change.routes.ts): اتصال LISTEN مباشر لكل instance نشط، وSSE بعمر 240 ثانية، مع إعادة اتصال وتحديث نسخ البيانات.
- [Catalog runtime](../src/storefront/catalog.js): فحص احتياطي كل 3 ثوانٍ في الإدارة و20 ثانية في المتجر عند غياب التحديث اللحظي (مع شروط النشاط).
- [Customer lifecycle](../src/storefront/platform/lifecycle.js): تحديث بيانات العميل والانتظار كل 15 ثانية للمسجلين، وفحص Dart Card leaderboard كل 30 ثانية عند تفعيله، وفحص الجلسة بفاصل 5 دقائق. مؤقت العرض المحلي للحجز ليس بالضرورة طلب شبكة.
- [Tracking](../Js/dart-tracking.js) و[Live operations](../Eye/dart-live-operations.js): فحوص تتبع سريعة تحتاج تقييدًا بالرحلات النشطة.
- [Catalog routes](../backend/src/modules/catalog/catalog.routes.ts): مدة CDN الحالية للكتالوج والإصدار 3 ثوانٍ.
- [Site settings](../backend/src/modules/settings/site-settings.routes.ts): خدمة قراءة الإعدادات تسبق فحص ETag وإرجاع 304؛ لا يعني 304 بالضرورة توفير SQL.
- [Brand details](../src/dashboard/brand-details.js): أحداث متعددة تبطل Cache التقارير المالية حتى دون تغيير مالي فعلي.
- [Cart expiry](../backend/src/modules/catalog/catalog.service.ts): تنظيف الحجوزات المنتهية موجود أصلًا عند قراءات معينة للمخزون؛ يجب المحافظة على اتساقه مع الشراء والانتظار.

قياس أولي من حسابات الإنتاج: فرع Neon الرئيسي كان في حالة idle عند الفحص، وإعداد السكون 300 ثانية، مع نطاق معالجة 0.25–1 CU. ظهرت مسارات التقارير المالية وإشعارات الإدارة والإعدادات وفحص الإصدارات ضمن أعلى مجموعات سجلات API. ذاكرة وظائف Vercel كانت أكبر بند استخدام غير الاشتراك في عينة يوم واحد. هذه مؤشرات لا تثبت وحدها السبب أو مقدار التوفير. لا نضع تفاصيل الفواتير أو بيانات العملاء أو الأسرار في المستودع العام. سجلات التشغيل ليست عدادًا لطلبات HTTP الفريدة.

## 4. التصميم المستهدف

المتصفح -> Cache للبيانات العامة -> API عند الحاجة -> Neon عند الحاجة الفعلية.
بعد نجاح المعاملة -> Outbox دائم / تحديث الإصدار -> إشعار أو تحديث النطاق المتأثر -> قراءة مصرح بها عند الحاجة.

| الوظيفة | الأسلوب المستهدف |
| --- | --- |
| المنتجات والصور والمحتوى العام | CDN Cache، مفاتيح إصدارات وإبطال عند التغيير حيث يدعمه النظام الحالي، TTL احتياطي |
| سعر ومخزون وخصم وحجز وشراء | تحقق خادمي مباشر ومعاملة ذرية؛ التعامل الواضح مع تغير السعر أو نفاد القطعة |
| الطلبات وحالاتها | تحديث فوري للمستخدم المنفذ، أحداث بعد COMMIT، تحديث النطاق المتأثر فقط |
| إشعارات الإدارة والعملاء | Web Push الموجود + قراءة مصرح بها عند فتح التطبيق، دون محتوى حساس في إشارات عامة |
| رسائل واتساب/بريد | Outbox الحالي وdispatch الفوري للأحداث المستحقة، retry دائم وفحص تعافٍ محدود |
| عيد الميلاد | مهمة يومية مستقلة بتوقيت القاهرة مع منع التكرار ومراعاة تغييرات البيانات خلال اليوم |
| رسالة التقييم بعد التسليم | available_at والجدولة الموجودة؛ الكود الحالي يحدد ساعة واحدة بعد التسليم (migration 0084)، لا تغيير للموعد |
| انتهاء الحجوزات | مؤقت محلي + تحقق ذري عند القراءة/الحجز/الشراء، تنظيف احتياطي محدود؛ عدم إطالة الحجز |
| المالية | تحميل عند فتح القسم، وإبطال Cache عند تغير مالي مؤثر فقط، توحيد الطلبات المتزامنة |
| بيانات العميل | تحميل عند الحاجة وفي الأقسام المناسبة، منع ازدواجية طلبات الحساب/الانتظار/التتبع |
| تتبع المندوب | أثناء رحلة نشطة فقط، تحديث عند حركة ذات معنى، حد أدنى وأقصى مناسب للفواصل |
| إعدادات المتجر | Cache للعرض العام فقط، إعادة تحقق عند الحاجة أو تغيير الإصدار |
| زيارات وإحصائيات | تجميع وإرسال دفعات عند الملاءمة، مع حفظ دقة العد ومراعاة الخصوصية |
| النسخ الاحتياطي وتنظيف السجلات | جدولة مستقلة أقل تكرارًا وفق احتياجات الاسترداد والأمان |
| Neon | استخدام الاتصالات الموجودة بكفاءة، السماح بالسكون، عدم فتح اتصال دائم بلا ضرورة |

### قواعد التنفيذ

- لا تشغيل لمؤقتات الشبكة عند إخفاء الصفحة أو مغادرة القسم ما لم تكن وظيفة ضرورية؛ التمييز بين مؤقت محلي وطلب HTTP واستعلام SQL.
- تجميع الطلبات المتزامنة، إلغاء الطلبات غير اللازمة، منع الطلبات القديمة من الكتابة فوق الحالة الأحدث.
- لا مشاركة Cache لبيانات العملاء أو الموظفين أو الأسعار الشخصية. الحفاظ على الفصل بين الحسابات والأدوار، RLS والصلاحيات وCSRF.
- SSE ليس سجل أحداث دائمًا؛ الاحتفاظ بإصدارات موثوقة ومصالحة عند إعادة الاتصال. قصر الاتصالات على الوظائف التي تحتاج سرعة فعلية، ثم قياس جدواها. إذا تعذر التحديث اللحظي دون خدمة إضافية، استخدام refresh عند الفتح أو الحدث وفحص احتياطي متكيف.
- لا حذف للفحص الاحتياطي قبل إثبات التعافي من الانقطاع. Outbox transactional، مفاتيح idempotency، محاولات مقيدة، backoff، ومراقبة تراكم الرسائل. لا الاعتماد على setTimeout داخل Vercel لمهام طويلة أو مؤجلة.
- استخدام GitHub Actions الحالي للمهام المجدولة؛ لا ادعاء أن جدولة دقيقة لمهام فردية متاحة بلا خدمات جديدة. اختيار الحد الأقصى المقبول للتأخير بالتجربة، وعدم تعطيل مهام مستحقة أثناء الهدوء إن تعارض ذلك مع سياسة العمل.

## 6. معايير القياس والقبول

- قياس طلبات HTTP الفريدة لكل مسار، واستعلامات SQL، ونسبة cache hit، وزمن استجابة p50/p95، ووقت نشاط Neon وCU-hours ونقل البيانات، واستدعاءات Vercel وCPU وProvisioned Memory. فصل تكاليف الاشتراك والبناء والتخزين عن تشغيل API.
- مقارنة نوافذ متماثلة وحمل متماثل؛ سيناريو خمول كامل، تصفح متجر، عميل مسجل، إدارة مفتوحة، طلب جديد، رحلة توصيل. رصد cold start عند السكون.
- هدف استرشادي: تقليل الطلبات غير الضرورية بنسبة 90% حيث تسمح الوظيفة، وتحديث الإشعارات اللحظية خلال 1–2 ثانية في الظروف الطبيعية حيث يدعم المسار ذلك. ليست ضمانات أو نتائج مقاسة.
- اختبارات عدم بيع نفس القطعة مرتين، انتهاء الحجز، تغير السعر، خصم/كوبون، إتمام الطلب كضيف، دمج العميل وفق السياسة المعتمدة، عدم خلط البيانات الشخصية، عدم تكرار الرسائل، إخفاق المزود وإعادة المحاولة، تغيّر الصلاحيات، عودة الاتصال، دقة المالية، وتتبع الرحلة.
- تشغيل اختبارات المشروع الحالية ذات الصلة وإضافة حالات الانحدار باستخدام أدوات الاختبار الموجودة. لا حزم جديدة.
- لا اعتبار أي مرحلة ناجحة دون دليل قياس واختبارات. التوفير المالي الفعلي يعتمد على الاستهلاك؛ لا وعد بفاتورة صفرية أو نسبة توفير محددة.

## 7. حالة هذا المستند

هذا المستند يسجل القرار والخطة فقط. لا يعني أن أي تعديل في كود التشغيل أو إعدادات البنية التحتية تم تنفيذه أو نشره. يجب تحديث حالة كل مرحلة بالأدلة والنتائج ومرجع Commit عند تنفيذها.
