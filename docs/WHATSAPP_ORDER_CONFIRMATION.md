# تأكيد الأوردر عبر واتساب

## السلوك

- الأوردر الجديد من Website يسجل رسالة Utility في نفس معاملة checkout. القالب `dart_order_confirmation`، اللغة العربية، المتغير الأول رقم الأوردر والثاني إجماليه النهائي بالجنيه بعد الخصومات. الأزرار بالترتيب Confirm ثم Cancel.
- زر Confirm ينقل New إلى Accepted ويثبت COD Verified داخل المعاملة نفسها. تظهر الحالة المقبولة في قائمة انتظار التجهيز القائمة؛ لا يوجد ضغط Accept إضافي.
- Cancel مسموح عبر هذه الرسالة في New أو Accepted فقط، ويعيد استخدام دالة انتقال الحالات الحالية للمخزون والخصومات. بعد بدء Preparing يلزم التواصل مع الإدارة.
- معرف طلب التأكيد عشوائي، ومربوط برقم الهاتف ونسخة الأوردر وإجماليه. التعديل الإداري يبطل الزر القديم. الصلاحية 24 ساعة؛ انتهاؤها لا يلغي الأوردر أو يحرر مخزونه تلقائيًا، بل يتركه للمراجعة اليدوية.
- يوجد منع تكرار بمعرف رسالة Meta وبحالة/نسخة الأوردر، وإقرار واحد لكل نتيجة. التأكيد المتأخر لا يعيد فتح أوردر ملغي. التأكيد لا يمنع إلغاءً لاحقًا قبل التجهيز.
- الإقرار نص عربي داخل نافذة الخدمة البالغة 24 ساعة من رسالة العميل. لا يرسل إقرار تأكيد معلق بعد إلغاء الأوردر، ولا أي إقرار بعد انتهاء نافذته. فشل الإقرار لا يتراجع عن قرار العميل.
- الـWebhook يثبت القرار قبل HTTP 200. الأخطاء العابرة ترجع 503 لإعادة التسليم. الإرسال الخارجي في outbox، والإرسال مجهول النتيجة لا يعاد آليًا.
- لا توجد رسائل تاريخية أو backfill. تبقى قنوات الحالات العادية Email/Push/in-site كما هي. بوابة مخاطر COD القائمة تظل تطبق عند بدء التجهيز.

## الملفات والإعداد

- Migration: `backend/migrations/0069_whatsapp_order_confirmation.sql`؛ جدول طلبات التأكيد وجدول الردود، مع RLS ومنع وصول أدوار المتصفح.
- الخدمة: `commerce.whatsapp.ts` تسجل الرسالة؛ `CommerceService.orderWhatsAppReply` يطبق القرار؛ `whatsapp-webhook.routes.ts` يستقبل الردين؛ `outbox.service.ts` يرسل القالب والإقرار.
- نفس endpoint الموجود: `/api/v1/webhooks/whatsapp` (GET للتحقق، POST للأحداث الموقعة). لا يوجد endpoint عام لتغيير الأوردر دون التوقيع وربط الهاتف.
- `WHATSAPP_ORDER_CONFIRMATION_ENABLED=true` يشغل رسائل التأكيد فقط، دون تغيير `WHATSAPP_SEND_ENABLED` الخاص بالرسائل السابقة.
- `WHATSAPP_ORDER_CONFIRMATION_TEMPLATE=dart_order_confirmation`، مع إعدادات Token وPhone Number ID وApp Secret وVerify Token القائمة. لا تحفظ الأسرار في المستودع.
- سجل الرسائل الحالي يعرض نوع الحدث والفئة والمحاولات وحالة التسليم؛ سجل التدقيق يربط القرار بالأوردر والعميل. هذه أعداد تشغيلية وليست فاتورة Meta.

## التحقق المنفذ

- `cd backend && npm run check`: 641 اختبارًا ناجحًا و53 متخطى؛ ESLint وTypeScript وإعداد Vercel ناجحة. الاختبارات المتخطاة تحتاج PostgreSQL منفصلًا.
- `cd backend && npm run build`: ناجح.
- 13 اختبارًا جديدًا على قاعدة PostgreSQL معزولة عبر PGlite: checkout ومنع تكرار الرسالة، المتغيرات والزرين، إرسال خارج نافذة المراجعات، تشغيل مستقل، قبول وتحقق ذريان، تكرار webhook والضغط، إلغاء قبل/بعد التأكيد وإعادة المخزون، مرسل مختلف، تغير النسخة/انتهاء الصلاحية/بدء التجهيز، rollback عند فشل ملكية القطعة ثم إعادة المحاولة، توقيع غير صحيح، وصيغتا button وinteractive، إقرار نصي ومنع الإقرار القديم والمنتهي.
- اختبارات المكافآت والخصومات القائمة نجحت ضمن فحص الخادم. لا يدعي PGlite اختبار تنافس اتصالات PostgreSQL حقيقية؛ الحماية تعتمد على قفل الأوردر وتحديث النسخة وقيود التفرد، ويشغل CI الاختبارات على PostgreSQL أيضًا.
- `node tests/database-authoritative-storage.cjs` و`node tests/security-boundaries.cjs`: ناجحان.
- فحص الواجهة الكامل رصد ملفات CSS/home.css وCSS/home.min.css قديمة عن المصدر في النسخة الموجودة؛ لم تعدل هذه الدفعة أي ملف واجهة أو CSS.
- لم ترسل الاختبارات المحلية رسائل حقيقية. اعتماد القالب وربط WABA باشتراك messages ونجاح تجربة فعلية ليست مثبتة بهذه الاختبارات.

|---|---|
| 1 حالات الواجهة والخطأ | ناجح: الأخطاء لا تكشف بيانات؛ لا واجهة جديدة تحتاج Loading؛ الرد القديم له توضيح |

| 4 التحقق والتفويض | ناجح: HMAC ورقم النشاط ورمز الطلب ورقم العميل وحالة الحساب؛ مسار Meta لا يستخدم صلاحيات موظف |
| 5 منع التكرار | ناجح: قيد الرسالة وانتقال الحالة وoutbox؛ unknown لا يعاد عشوائيًا |
| 6 التدقيق | ناجح: سجل طلب التأكيد والرد والقرار وأحداث الأوردر وCOD |
| 7 التكلفة والخدمة | ناجح بالكود: Utility للتأكيد وService للإقرار وسجل محاولات؛ اعتماد Meta الحي غير متحقق |
| 8 عدم التأثير خارج النطاق | ناجح لفحوص الخادم والأمان؛ مشكلة CSS سابقة ومذكورة أعلاه |
| 9 الاختبارات | ناجح ضمن الفحوص المذكورة؛ لا تجربة رسالة حقيقية أو ادعاء لاختبار كل التكاملات |
| 10 الأسرار | ناجح: لا أسرار جديدة بالكود أو الواجهة |

## اختبار التشغيل اليدوي

أنشئ أوردرًا على رقم اختبار تتحكم فيه، وافحص وصول القالب ورقم الأوردر وإجماليه. اضغط Confirm: يجب ظهور Accepted وVerified ثم إمكان Preparing. أنشئ أوردرًا ثانيًا واضغط Cancel: يعود المخزون ولا تتكرر الاستعادة عند الضغط مجددًا. اختبر الرقم الخاطئ والزر القديم بعد تعديل الأوردر. تابع سجل الرسائل والتدقيق. لا تعتبر Published إثبات Read؛ إيصالات Meta مستقلة.
