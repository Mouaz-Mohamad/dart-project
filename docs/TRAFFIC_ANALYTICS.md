# Website traffic identity and shared periods

Updated 2026-10-22.

Guests keep their existing first-party browser UUID in `dart_vid` (one year, refreshed on visits). A sessionStorage fallback keeps it across navigation if cookies cannot be read or saved. Only an identifier is stored: all events, counters, profiles and reports remain in PostgreSQL. Clearing site data, private browsing or changing browser/profile can create another anonymous visitor; this is browser-level estimation, not guaranteed physical-device identification. No IP matching or fingerprinting is introduced.

The dashboard displays `visit-1`, `visit-2`, etc. PostgreSQL owns these numbers in `traffic_analytics_visitors`. Migration 0062 backfills existing identities in first-event order, then an event insert trigger allocates numbers for new visitors. Mapping inserts use unique constraints and conflict handling; existing codes are never regenerated by another event, session, server restart or report range. Sequence numbers can have gaps after concurrent conflicts/rollbacks and are not a visitor-count metric. Previously distinct anonymous identities are not merged without evidence.

The existing UUID request field remains compatible. Signed-in visitors use their server-authenticated account name/client code and are counted once across browsers. When a customer signs in, the browser sends a best-effort visit event using the existing session; its unique event key prevents a second visit count while the service links guest history to the account. Analytics does not delay authentication, cart or checkout.

Hours, Daily, Weekly, Monthly and Yearly all use the Brand general period. Hours aggregates activity into 24 Cairo hours across that entire period, including annual/custom selections up to the existing 3660-day limit. The separate 1/7/30-day hourly selector is removed. The total period unique-visitors metric is not the sum of per-hour distinct counts: one visitor may appear in multiple hour buckets.

Last Year is the preceding full calendar year. Its comparison is the full calendar year before it, including leap years, and its selection persists through the existing period preference. Brand and Finance controls stay synchronized.

## Deployment and recovery

Apply migration 0062 explicitly before publishing the API. It is additive, transactional, enables RLS and revokes PUBLIC/anonymous access to the mapping table and sequence. Its trigger supports older API instances during rollout. Record the exact source checksum in `dart_schema_migrations` using the existing migration lock. No orders, stock, discounts or financial records are modified. If the release must be reverted, the prior application remains compatible with the additive table/trigger; retain the mapping rather than deleting visitor history.
